## 🔍 CloudForge 项目评审

### 先讲优点（确实不错）

- **技术栈覆盖面广**：PaaS 层和 SaaS 层都有涉及，面试能聊的东西多
- **端到端闭环**：代码→CI→镜像→部署→监控→告警，这是面试官爱看的完整链路
- **面试亮点提炼得好**：你已经在从"面试怎么说"的角度思考了，方向对

---

### ⚠️ 核心问题（三个致命的）

**1. 范围过大，可信度会崩**

一个人做一个"用户中心 + CRUD + 异步任务 + K8s 部署 + CI/CD + 全链路监控 + 告警 + 混沌工程"的平台，有经验的老手全职也要 3-4 个月。面试官看到一个大二学生列这么多，第一反应不是"好厉害"，而是"你每个都只做了 5% 吧"。

**建议**：砍到 **一个核心故事线**。要么以"平台工程"为主线（部署+监控+CI/CD），用一个极简 demo app 作为被部署对象；要么以"可观测性微服务"为主线，部署到托管 K8s，把深度做出来。

**2. "手动二进制部署 K8s"是把双刃剑**

技术上确实能体现理解深度，但：
- 极其耗时，这些时间不如花在 GitOps、Terraform、OpenTelemetry 等差异化技能上
- 面试官很容易追问到你不会的地方（etcd Raft 共识、CNI 插件原理、kubelet 证书轮换）
- 业界最佳实践本就是 kubeadm/k3s，手动部署反而显得不够工程化

**建议**：用 **k3s 快速搭集群 + 深入讲解架构**。省下来的时间投入更有区分度的方向。

**3. 缺少具体业务场景，读起来像技术全家福**

"中小团队缺乏标准化交付与监控体系"是万金油描述。面试官会问："谁在用？解决了谁什么问题？"

**建议**：虚构但具体的场景，比如：

> "一个 3 人创业团队的 SaaS 应用，每次上线靠 scp 传代码 + 手动重启，出问题靠用户报修。我给他们搭了一套从 git push 到自动部署、自动监控的流水线。"

## 📋 改动总结

### 1. 从"平台全家桶"收缩为"一条清晰故事线"

**原来**：用户中心、CRUD、异步任务、K8s、CI/CD、监控、告警、混沌工程... 十几个模块铺开

**现在**：聚焦三件事 ——
- **CloudForge Pipeline**：代码推送到 Git → GitHub Actions → 构建镜像 → ArgoCD 金丝雀发布
- **Observability Stack**：OpenTelemetry 采集 → Prometheus + Loki + Tempo → Grafana 统一看板
- **Demo Service**：一个带健康检查、结构化日志、Prometheus 指标的极简 FastAPI 服务

**为什么**：每个模块你都能做到 80% 深度，而不是 10 个模块各做 5%。面试官问任何一个点你都有东西聊。

### 2. 引入 ArgoCD + Terraform，打造差异化

这是大部分实习生项目没有的东西。ArgoCD 的 GitOps 模式和 Terraform 的 IaC 理念，是云原生方向面试的高频考点。

### 3. 用 k3s 替代手动二进制部署

节省大量时间，但不丢分。关键是你要能解释 k3s 相比标准 K8s 少了什么、用什么替代的（比如 SQLite 代替 etcd），这反而体现了理解深度。

### 4. 加入 OpenTelemetry 分布式追踪

Prometheus + Loki 很多人都搭过，但 OTel + Tempo 的追踪链路串联是大部分人没做过的，面试亮点。

### 5. 安全部分补充了具体措施

Sealed Secrets、NetworkPolicy、非 root 容器、只读文件系统 —— 每一条都是面试能展开的点。

### 6. 验收标准写成可验证项

每一条都可以在面试时演示：看 Grafana 看板、触发金丝雀发布、查 TraceId...

### 7. 风险标注

在文档里标注了"演示环境简化"的地方（Redis 复用、单点 PostgreSQL 等），面试官追问时你说出"这里我知道简化了，生产应该怎么改进"，比回避问题加分太多。
