
# CloudForge Implementation Plan — Upgrade from SDD Draft to Production-Ready

## Summary

The CloudForge codebase is ~80% complete relative to the SDD draft. All major subsystems exist: FastAPI CRUD microservice, Helm chart (14 templates), GitHub Actions CI with multi-arch build, ArgoCD Application, OpenTelemetry instrumentation, Prometheus metrics, alert rules, k3d/k6 scripts, and documentation (README, 3 ADRs, ROADMAP). This plan addresses the **remaining 20%** — the concrete gaps that prevent the draft's acceptance criteria from being fully satisfied — and adds quality hardening.

---

## Pre-Mortem Risk Analysis

### Tigers (real risks — act on them)

| Risk | Classification | Mitigation |
|------|---------------|------------|
| **Grafana dashboards are stub JSON** — missing schema fields (`__inputs`, `__requires`, `schemaVersion`, `templating`, `time`, `timepicker`); won't import into real Grafana | **Launch-Blocking** | Rewrite both dashboard JSONs against the Grafana 10.x schema; validate by importing into a running Grafana instance |
| **Structured logging format** — structlog uses `ConsoleRenderer` (human-readable); Loki/Promtail cannot parse trace_id/span_id/request_id for log-to-trace correlation | **Launch-Blocking** | Switch to JSON renderer in production/K8s mode; keep console for local dev via env toggle |
| **Helm one-command deploy** — PostgreSQL and Redis are external `helm install` calls, not declared as Chart dependencies; violates "一条命令部署" | **Launch-Blocking** | Add PostgreSQL and Redis as Helm dependencies in `Chart.yaml` with conditionals |
| **/metrics endpoint < 40 lines** — `prometheus-fastapi-instrumentator` with default config may produce ~25–30 lines; the draft requires 40+ | **Fast-Follow** | Add custom business metrics (task count by status, DB connection pool stats) via `prometheus_client` |
| **Docker image size unverified** — Dockerfile multi-stage is correct but untested against the < 100MB target | **Track** | Build and measure; if > 100MB, slim dependencies in builder stage |

### Paper Tigers (document to align)

- "k3d vs real K8s" — already addressed by ADR-001; no action needed
- "ArgoCD vs Flux" — already addressed by ADR-002; no action needed
- "No JWT auth" — explicitly scoped out in non-goals; no action needed
- "No Terraform" — explicitly scoped out; no action needed

### Elephants (unspoken — investigate)

- None surfaced during audit. The draft is explicit about scope boundaries.

## Steps

### Phase 1: Grafana Dashboard Hardening (highest-value fix)

- [ ] **Step 1: Rewrite `dashboards/cloudforge-overview.json` as valid Grafana 10.x dashboard JSON**
  - Add full schema: `__inputs: []`, `__requires: []`, `schemaVersion: 39`, `version: 1`, `graphTooltip: 0`, `editable: true`, `time: {from: "now-1h", to: "now"}`, `timepicker: {}`, `templating: {list: []}`, `refresh: "30s"`, `links: []`
  - Upgrade panels from stub `"type": "graph"` to `"timeseries"` (Grafana 10 native) with proper `fieldConfig`, `options`, `targets`
  - 4 panels: Request Rate (timeseries, QPS by method/handler), Error Rate (timeseries, 5xx ratio), p95 Latency (timeseries, histogram_quantile), Status Code Distribution (bargauge or stat)
  - Add datasource variable `{"type": "datasource", "name": "DS_PROMETHEUS", "query": "prometheus"}` in templating

- [ ] **Step 2: Rewrite `dashboards/cloudforge-k8s.json` as valid Grafana 10.x dashboard JSON**
  - Same full schema as above
  - 4 panels: CPU Usage (timeseries, per-pod), Memory Usage (timeseries, per-pod MB), Replica Count (timeseries, desired vs available overlay), Pod Restarts (stat, rate over 5m)
  - Add datasource variable for Prometheus

- [ ] **Step 3: Create Grafana dashboard ConfigMap and provisioner in Helm chart**
  - New template: `chart/templates/grafana-dashboards-cm.yaml` — a ConfigMap with `label: grafana_dashboard: "1"` containing both dashboard JSONs
  - Update `scripts/setup-observability.sh` to pass `--set grafana.sidecar.dashboards.enabled=true` when installing kube-prometheus-stack (or document manual import via Grafana UI)

### Phase 2: Structured Logging & Loki Correlation (launch-blocking)

- [ ] **Step 4: Add JSON log renderer toggle to `app/main.py`**
  - Read `CF_LOG_FORMAT` env var (values: `console` | `json`), default to `console` for local dev
  - When `json`: use `structlog.processors.JSONRenderer()` instead of `ConsoleRenderer()`
  - Ensure `trace_id`, `span_id`, `request_id` appear as top-level JSON keys (already bound via middleware)
  - Set `CF_LOG_FORMAT=json` in the Helm chart ConfigMap template for K8s deployments

- [ ] **Step 5: Verify Loki log-to-trace correlation**
  - Confirm Promtail in `loki-stack` captures container stdout (it does by default)
  - Confirm Loki datasource is added in Grafana setup instructions
  - Add a note in README showing how to jump from a log line to a Tempo trace using `trace_id`

### Phase 3: Helm One-Command Deploy (launch-blocking)

- [ ] **Step 6: Add PostgreSQL and Redis as Helm dependencies in `Chart.yaml`**
  - Add `dependencies` block:
    ```yaml
    dependencies:
      - name: postgresql
        version: "~15.5"
        repository: "oci://registry-1.docker.io/bitnamicharts"
        condition: postgresql.enabled
      - name: redis
        version: "~19.5"
        repository: "oci://registry-1.docker.io/bitnamicharts"
        condition: redis.enabled
    ```
  - Add `postgresql.enabled: true` and `redis.enabled: true` to `values.yaml`
  - Update `values.yaml` PostgreSQL section to use Bitnami subchart values:
    ```yaml
    postgresql:
      enabled: true
      auth:
        database: cloudforge
        username: cloudforge
        password: cloudforge
    redis:
      enabled: true
      auth:
        enabled: false
      architecture: standalone
    ```
  - Update `secret.yaml` template to reference subchart service names (`{{ .Release.Name }}-postgresql`, `{{ .Release.Name }}-redis-master`)

- [ ] **Step 7: Update `scripts/setup-k3d.sh` to include `helm dependency update`**
  - Add `helm dependency update ./chart` step before `helm install`
  - Remove standalone `helm install postgresql ...` and `helm install redis ...` commands from README (they're now dependencies)

### Phase 4: Metrics Enrichment (fast-follow)

- [ ] **Step 8: Add custom Prometheus metrics in `app/core/metrics.py`**
  - `cloudforge_tasks_total` (Gauge, by status): count of tasks per status enum value
  - `cloudforge_db_pool_size` (Gauge): SQLAlchemy connection pool stats
  - Register these on the same `CollectorRegistry` used by the instrumentator
  - Add a periodic background task in the FastAPI lifespan to update task counts (or compute on scrape via a custom endpoint)

- [ ] **Step 9: Verify `/metrics` endpoint output reaches 40+ lines**
  - After Step 8, the instrumentator defaults (~25) + custom metrics (~5) + Python platform metrics should reach 40+
  - Run `curl -s http://localhost:8000/metrics | grep -v '^#' | grep -v '^$' | wc -l` to validate
  - If still below 40, add `python_info`, `process_*` metrics via `prometheus_client` default collector

### Phase 5: Quality Hardening (should-do)

- [ ] **Step 10: Add `app/tests/test_metrics.py` — test the /metrics endpoint**
  - Assert 200 status
  - Assert response is not empty
  - Assert at least 40 non-comment, non-empty lines
  - Assert required metric families are present: `http_requests_total`, `http_request_duration_seconds_bucket`, `cloudforge_tasks_total`

- [ ] **Step 11: Add `app/tests/test_logging.py` — test structured log format**
  - Verify `CF_LOG_FORMAT=json` produces valid JSON lines
  - Verify JSON output includes `trace_id`, `span_id` fields (within an OTel span context)

- [ ] **Step 12: Docker image size validation**
  - Document the measured image size in README (build and verify)
  - If > 100MB: prune unnecessary packages in builder stage; verify only `libpq` is kept in runtime

- [ ] **Step 13: Add `helm lint` and `helm template` smoke test to CI**
  - New CI job (or extend existing `test` job): `helm lint ./chart && helm template cloudforge ./chart --debug`
  - Catches template syntax errors before merging

- [ ] **Step 14: Grafana dashboard import smoke test**
  - Add a CI step that validates both JSON files are syntactically valid JSON and contain required top-level keys (`title`, `uid`, `panels`, `schemaVersion`)

### Phase 6: Documentation Polish (M6 completion)

- [ ] **Step 15: Update README — one-command deploy section**
  - After Phase 3, the flow becomes:
    ```bash
    bash scripts/setup-k3d.sh
    bash scripts/setup-observability.sh
    helm dependency update ./chart
    helm install cloudforge ./chart
    ```
  - Remove standalone PostgreSQL/Redis install commands

- [ ] **Step 16: Update README — Grafana dashboard import instructions**
  - Document both auto-provisioned (sidecar) and manual import (upload JSON) paths
  - Add screenshots or ASCII diagram of the final Grafana dashboard layout

- [ ] **Step 17: Verify all 3 ADRs are self-contained**
  - ADR-001 (k3s), ADR-002 (ArgoCD), ADR-003 (OTel) — already complete
  - No changes needed; just confirm they follow the format: Status → Context → Decision → Rationale → Tradeoffs → Consequences
