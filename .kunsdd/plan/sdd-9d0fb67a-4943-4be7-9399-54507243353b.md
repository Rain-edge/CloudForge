# CloudForge Implementation Plan

## Summary

Build CloudForge — a GitOps-driven cloud-native microservice operations platform. A FastAPI CRUD service (Task Manager) is containerized, deployed to k3s via Helm + ArgoCD, monitored through OpenTelemetry / Prometheus / Grafana / Loki / Tempo, and hardened with HPA, canary releases, and load-testing to 500+ QPS. The project serves as a cloud-computing internship portfolio piece.

## Pre-mortem

### Tigers

| # | Risk | Severity | Classification | Mitigation |
|---|------|----------|---------------|-------------|
| T1 | k3d/k3s networking (Ingress, LoadBalancer) breaks on Windows; student blocked at M3 | Launch-Blocking | Tiger | **Fallback**: use Docker Desktop K8s or Minikube with `--driver=docker`. Add a troubleshooting section in README. Decision by M3-start. |
| T2 | Multi-arch build (`linux/arm64`) fails in GitHub Actions due to QEMU timeout or disk space | Launch-Blocking | Tiger | **Mitigation**: split build matrix; set `QEMU_OPTS="-cpu max"`; test single-arch fallback. If multi-arch fails repeatedly, ship amd64-only and document arm64 as "planned." |
| T3 | OTel SDK + Tempo integration produces no traces (bad exporter config) | Fast-Follow | Tiger | **Mitigation**: start with console exporter to verify traces locally before wiring Tempo. Add debug logging to OTel config. |
| T4 | Canary Ingress annotations differ between Ingress-Nginx versions; rollback never triggers | Fast-Follow | Tiger | **Mitigation**: pin Ingress-Nginx version in Helm values; test canary weight 0%→100% manually before scripting. |
| T5 | `500 QPS` target unreachable on single-node k3s (laptop CPU/memory ceiling) | Track | Tiger | **Mitigation**: report actual QPS honestly; document that bottleneck was hardware, not code. The *shape* of the HPA curve matters more than the absolute number. |

### Paper Tigers

| # | Risk | Why it's a Paper Tiger |
|---|------|------------------------|
| PT1 | "ArgoCD is overkill for one service" | Agreed for production. This is a learning project — the goal is demonstrating GitOps competency. Document this tradeoff honestly. |
| PT2 | "Terraform + local k3d is weird" | IaC principle (declarative infra) is the point, not the cloud bill. If Terraform adds too much friction, replace with a single `setup-k3d.sh` and note Terraform as a future enhancement. |

### Elephants

| # | Risk |
|---|------|
| E1 | OpenTelemetry has a steep learning curve. If the student can't debug a broken trace pipeline, M4 stalls. Resolution: trace-first approach — instrument one endpoint, verify it end-to-end before instrumenting others. |
| E2 | Scope creep: the "just one more feature" temptation during M4/M5. Resolution: hard-cap each milestone to its checklist; new ideas go into a `ROADMAP.md` deferred section. |

## Implementation Steps

### Phase 1: Scaffold & Local Dev Environment (M1)

#### Step 1.1: Initialize project repository
- [ ] Create monorepo at `github.com/<user>/cloudforge` with `.gitignore` (Python, Node, Terraform, K8s)
- [ ] Initialize `pyproject.toml` with Python 3.11, FastAPI, uvicorn, SQLAlchemy, alembic, pydantic, pytest dependencies
- [ ] Create directory structure per the draft: `app/`, `chart/`, `dashboards/`, `scripts/`, `.github/workflows/`, `argocd/`, `docker/`
(covers: M1)

#### Step 1.2: Implement FastAPI Task Manager service
- [ ] `app/main.py`: FastAPI app factory with lifespan handler for DB connection pool startup/shutdown
- [ ] `app/models/task.py`: SQLAlchemy model — `id` (UUID), `title` (str), `status` (enum: pending/in_progress/done), `created_at`, `updated_at`
- [ ] `app/schemas/task.py`: Pydantic v2 models for `TaskCreate`, `TaskUpdate`, `TaskResponse`
- [ ] `app/routers/tasks.py`: CRUD endpoints — `GET /tasks`, `POST /tasks`, `GET /tasks/{id}`, `PATCH /tasks/{id}`, `DELETE /tasks/{id}`
- [ ] `app/routers/health.py`: `GET /health` returning `{"status": "ok", "db": "connected"|"error"}`
- [ ] `app/middleware/logging.py`: request-ID middleware injecting `X-Request-ID` header and structured logging via `structlog`
- [ ] `app/core/config.py`: settings via `pydantic-settings` reading from env vars (`DATABASE_URL`, `REDIS_URL`, `SECRET_KEY`)
- [ ] `app/core/database.py`: async SQLAlchemy engine + session factory (asyncpg driver)
(covers: M1)

#### Step 1.3: Add Alembic for database migrations
- [ ] `alembic init alembic`, wire `alembic.ini` to `app/core/database.py`
- [ ] Generate initial migration for `tasks` table
- [ ] Test: `alembic upgrade head` creates table, `alembic downgrade -1` drops it
(covers: M1)

#### Step 1.4: Docker Compose local stack
- [ ] `docker-compose.yml`: services for `app` (build context `.`, hot-reload via volume mount), `postgres` (14-alpine), `redis` (7-alpine)
- [ ] `.env.example`: `DATABASE_URL=postgresql+asyncpg://cloudforge:cloudforge@postgres:5432/cloudforge`
- [ ] Smoke test: `docker compose up` → `curl localhost:8000/health` → `curl localhost:8000/docs`
(covers: M1)

#### Step 1.5: Pytest suite for CRUD endpoints
- [ ] `app/tests/conftest.py`: `httpx.AsyncClient` fixture, test DB via `aiosqlite` or ephemeral Postgres
- [ ] `app/tests/test_health.py`: assert `/health` returns 200 and `db: connected`
- [ ] `app/tests/test_tasks.py`: test create (201), list (200, empty then with items), get (200/404), update (200/404), delete (204/404), invalid payload (422)
- [ ] Run: `pytest -v` — all green
(covers: M1)

### Phase 2: Containerization & CI (M2)

#### Step 2.1: Multi-stage Dockerfile
- [ ] `docker/Dockerfile`:
  - Stage 1 (`builder`): `python:3.11-slim`, install poetry/pip, copy deps, install
  - Stage 2 (`runtime`): `python:3.11-alpine`, copy venv + app code, create `cloudforge` user (UID 1000)
  - `USER cloudforge`, `EXPOSE 8000`, `CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0"]`
  - `.dockerignore`: exclude `__pycache__`, `.git`, `tests/`, `venv/`
- [ ] Verify: `docker build -f docker/Dockerfile -t cloudforge:latest . && docker images cloudforge` — image < 100MB
(covers: M2)

#### Step 2.2: GitHub Actions CI pipeline
- [ ] `.github/workflows/ci.yml`:
  - Trigger: `push` to `main`, `pull_request` to `main`
  - Job 1 `test`: checkout → setup Python 3.11 → install deps → `pytest --junitxml=results.xml`
  - Job 2 `build-push` (needs `test`):
    - Login to Docker Hub via `docker/login-action`
    - Set up QEMU + `docker/build-push-action` for multi-arch (`linux/amd64,linux/arm64`)
    - Tags: `latest`, `sha-${GITHUB_SHA::7}`
    - Push to `DOCKERHUB_USERNAME/cloudforge`
  - Job 3 `update-manifest` (needs `build-push`):
    - Checkout a separate `cloudforge-manifests` repo (or same repo `argocd/` dir)
    - `yq` or `sed` to bump image tag in `argocd/app-deployment.yaml`
    - Commit + push (triggers ArgoCD sync)
- [ ] Test: push a commit, verify Actions run green, image appears on Docker Hub
(covers: M2)

#### Step 2.3: Multi-arch validation
- [ ] Pull image on amd64 machine → `docker run -p 8000:8000 cloudforge`, `/health` works
- [ ] Pull image on arm64 machine (or verify via `docker buildx imagetools inspect`) — both architectures present
- [ ] If arm64 fails in CI: document fallback (amd64-only), keep arm64 as `ROADMAP.md` item
(covers: M2)

### Phase 3: Kubernetes Deployment & GitOps (M3)

#### Step 3.1: Local cluster provisioning
- [ ] `scripts/setup-k3d.sh`:
  - Install k3d if missing (`choco install k3d` / `brew install k3d`)
  - `k3d cluster create cloudforge --servers 1 --agents 2 -p "80:80@loadbalancer" -p "443:443@loadbalancer"`
  - Install `kubectl` + `helm` if missing
  - Verify: `kubectl cluster-info`, `kubectl get nodes` (3 nodes ready)
- [ ] Platform note: k3d runs in Docker, works on Windows/macOS/Linux. If k3d fails, fallback to Docker Desktop K8s.
(covers: M3)

#### Step 3.2: Helm Chart
- [ ] `chart/Chart.yaml`: apiVersion v2, name `cloudforge`, version `0.1.0`
- [ ] `chart/values.yaml`: image repo/tag, service type ClusterIP, Ingress host, DB/Redis connection strings, HPA min/max replicas, resource limits
- [ ] `chart/templates/deployment.yaml`: Deployment with `readinessProbe` + `livenessProbe` on `/health`, `securityContext.runAsUser: 1000`, `readOnlyRootFilesystem: true`
- [ ] `chart/templates/service.yaml`: ClusterIP on port 8000
- [ ] `chart/templates/ingress.yaml`: Ingress with annotations for optional canary (see Step 5.4)
- [ ] `chart/templates/configmap.yaml`: non-sensitive config (log level, etc.)
- [ ] `chart/templates/secret.yaml`: DB password, secret key (note: sealed-secrets for production, plain for demo)
- [ ] `chart/templates/hpa.yaml`: CPU 70% target, min 2 max 10
- [ ] `chart/templates/pdb.yaml`: minAvailable 1
- [ ] Test: `helm lint chart/`, `helm template cloudforge chart/` — output valid
(covers: M3)

#### Step 3.3: Infrastructure dependencies on K8s
- [ ] Install PostgreSQL via Helm: `helm install postgresql oci://registry-1.docker.io/bitnamicharts/postgresql --set auth.database=cloudforge`
- [ ] Install Redis via Helm: `helm install redis oci://registry-1.docker.io/bitnamicharts/redis`
- [ ] Verify: `kubectl get pods` — postgresql + redis running
(covers: M3)

#### Step 3.4: Deploy CloudForge app
- [ ] Update `values.yaml` with actual DB/Redis connection strings from Step 3.3
- [ ] `helm install cloudforge ./chart` → `kubectl get pods` → 2 replicas running
- [ ] Port-forward to test: `kubectl port-forward svc/cloudforge 8000:8000` → `/health` OK, `/docs` accessible
(covers: M3)

#### Step 3.5: Install and configure ArgoCD
- [ ] `kubectl create namespace argocd`
- [ ] `kubectl apply -n argocd -f https://raw.githubusercontent.com/argoproj/argo-cd/stable/manifests/install.yaml`
- [ ] `argocd/cloudforge-app.yaml`:
  - Application targeting the same repo, path `chart/`, destination namespace `cloudforge`
  - Sync policy: automated (prune=true, selfHeal=true)
- [ ] `kubectl apply -f argocd/cloudforge-app.yaml`
- [ ] Verify: `argocd app get cloudforge` — Synced & Healthy
- [ ] End-to-end test: push a config change (e.g., replica count) → ArgoCD syncs within 3 minutes
(covers: M3)

#### Step 3.6: Ingress & Canary baseline
- [ ] Install Ingress-Nginx via Helm: `helm install ingress-nginx ingress-nginx/ingress-nginx`
- [ ] Update `chart/templates/ingress.yaml` with host rule (e.g., `cloudforge.local`)

- [ ] `chart/templates/prometheusrule.yaml`:

- [ ] Verify: manually trigger 500 errors via a test endpoint → alert fires → webhook receives payload
(covers: M4)

### Phase 5: Resilience Validation (M5)

#### Step 5.1: HPA verification
- [ ] Deploy with HPA min=2, max=10, CPU target 70%
- [ ] Run load test (Step 5.3) → watch `kubectl get hpa cloudforge -w` → replicas scale from 2 → N
- [ ] After load stops → replicas cool down to 2 within 5 minutes
- [ ] Verify: `kubectl describe hpa` shows scaling events
(covers: M5)

#### Step 5.2: Graceful shutdown & probe validation
- [ ] Graceful shutdown: in `app/main.py` lifespan, catch SIGTERM, `await asyncio.sleep(5)` to drain in-flight requests before closing DB pool
- [ ] Test: `kubectl delete pod cloudforge-xxx` → during deletion, `curl /tasks` still responds until pod terminates
- [ ] Readiness Probe: `GET /health` fails → pod removed from Service endpoints
- [ ] Liveness Probe: `GET /health` fails after 3 consecutive → pod restarted
- [ ] Test: simulate DB disconnect → readiness fails → traffic stops; recovery → readiness passes → traffic resumes
(covers: M5)

#### Step 5.3: Load testing with k6
- [ ] `scripts/load-test.js`:
  - k6 script: ramp-up 0→50 VUs over 30s, sustain 50 VUs for 2 minutes, ramp-down
  - Target: `GET /tasks` and `POST /tasks` mix (80/20)
- [ ] Run: `k6 run scripts/load-test.js`
- [ ] Collect: actual peak QPS, p95 latency under load, HPA scale-up time
- [ ] Document results in `LOAD_TEST_REPORT.md` with screenshots of Grafana dashboards during test
- [ ] Target: 500+ QPS sustained. If hardware-limited, document actual number and explain why it's still valid (bottleneck was CPU not code)
(covers: M5)

#### Step 5.4: Canary release with rollback
- [ ] Create `chart/templates/ingress-canary.yaml` with weight annotation
- [ ] Deploy "canary" version (e.g., add a `GET /version` returning `v2` with a deliberate latency injection)
- [ ] Set canary weight: 10% → verify via `curl -H "Host: cloudforge.local"` hitting v2 ~10% of requests
- [ ] Set canary weight: 50% → verify
- [ ] Simulate "failure": canary pods return 500 errors → Prometheus alert fires → manually (or via ArgoCD) rollback by deleting canary Deployment
- [ ] Document the canary flow in README with commands and screenshots
(covers: M5)

#### Step 5.5: Chaos injection (optional spice)
- [ ] `kubectl delete pod <postgres-pod>` → app readiness probe should handle it (fail → recover)
- [ ] `kubectl cordon <node>` → pods reschedule to other nodes (if multi-node k3d)
- [ ] Document: "alert fired within X seconds, app self-healed within Y seconds"
(covers: M5)
