CloudForge 第一周：FastAPI 核心架构

总览：一个 HTTP 请求的完整旅程

当你在终端输入 curl http://localhost:8000/tasks 并按下回车时，CloudForge 内部发生了一场精密的编排。理解这场旅程，你就理解了这个项目的骨架。

┌─────────────┐ ┌──────────────┐ ┌───────────────┐ ┌────────────────┐ │ Uvicorn │────▶│ FastAPI │────▶│ Middleware │────▶│ Router │ │ (ASGI 服务) │ │ (路由匹配) │ │ (RequestID) │ │ (tasks.py) │ └─────────────┘ └──────────────┘ └───────────────┘ └────────────────┘ │ ▼ ┌────────────────┐ │ ORM / Schema │ │ (Pydantic) │ └────────────────┘ │ ▼ ┌────────────────┐ │ Database │ │ (PostgreSQL) │ └────────────────┘

第一讲：app/main.py — 应用的入口

这是整个项目的 main 函数，所有其他模块都从这里被组装起来。

核心结构

模块代码行做的事情
lifespan28-53启动时验证 PG 就绪 → 自动建表；关闭时释放连接池
app = FastAPI(...)58-63创建应用实例，绑定 lifespan
setup_telemetry(app)67OpenTelemetry 自动生成 Trace
RequestIDMiddleware71每个请求注入唯一 ID + trace_id
setup_metrics(app)74暴露 /metrics 给 Prometheus
health.router77注册 GET /health 路由
tasks.router78注册 CRUD /tasks 路由
关键概念：lifespan
FastAPI 的 lifespan 是一个 async context manager（用 @asynccontextmanager 装饰）。yield 之前的代码在启动时执行，之后的代码在关闭时执行。这替代了旧的 @app.on_event("startup") 写法。
关键概念：中间件加载顺序
FastAPI 按 add_middleware() 的逆序执行中间件。所以 setup_telemetry → RequestIDMiddleware → setup_metrics 的实际执行顺序是 setup_metrics → RequestIDMiddleware → setup_telemetry。为什么先 setup_telemetry？因为 OpenTelemetry 需要先生成 Span，其他中间件才能读取 trace_id。

启动时发生了什么

1
engine.connect() 尝试连 PostgreSQL，最多重试 10 次（每次等 2 秒）。这是对 Docker Compose depends_on 的二次确认——容器启动不代表 PG 真正 ready。
2
Base.metadata.create_all 自动创建 tasks 表。生产环境应该用 alembic 管理迁移，但演示环境这么做更方便。
3
可观测性三件套注册：Telemetry → Logging → Metrics。
4
路由注册：/health、/metrics、/tasks、/tasks/{id} 全部可用。

第二讲：app/core/config.py — 环境变量管理

这个文件只有 42 行，但它解决了软件工程里一个根本问题：如何让同一份代码在不同环境下使用不同的配置？

配置优先级

环境变量 (CF_DATABASE_URL) ← 最高优先级 │ ▼ .env 文件（项目根目录） ← 次优先级 │ ▼ 代码中的 default 值 ← 最低优先级（兜底）
设计巧思：CF_ 前缀
pydantic-settings 自动把 Python 字段名 database_url 转大写并加 CF_ 前缀 → 环境变量 CF_DATABASE_URL。这样 CloudForge 的变量不会和系统的 DATABASE_URL 冲突。

验证：在 Docker Compose 中 - CF_DATABASE_URL=postgresql+asyncpg://... 会覆盖代码默认值。

第三讲：app/core/database.py — 异步数据库引擎

这是整个项目性能的关键。如果数据库连接管理不好，应用在高并发下会崩溃。

连接池参数解析

参数值为什么选这个值
pool_pre_pingTrue每次从池子取连接前先 SELECT 1。如果 PG 重启过或空闲超时断开了，自动重连。
pool_size10保持 10 个常驻连接，应对常规流量。
max_overflow20流量高峰时最多临时创建 20 个额外连接，峰值 10+20=30。
pool_recycle3600连接超过 1 小时自动回收。防止云环境负载均衡器静默断开空闲连接。
timeout10s建立新 TCP 连接的超时。超时则快速失败，不阻塞。
command_timeout30s单条 SQL 最长执行时间。防止慢查询卡住连接。
为什么用 asyncpg 而不是 psycopg？
asyncpg 是纯 Python 写的异步 PG 驱动，速度比 psycopg2 快 3 倍以上。SQLAlchemy 2.0 原生支持 async，搭配 asyncpg 实现真正的非阻塞数据库操作。

依赖注入：get_db

async def get_db():
    async with async_session() as session:
        yield session

这是一个 Python generator。在路由函数中声明 db: AsyncSession = Depends(get_db) 后，FastAPI 会在请求开始时创建 session，请求结束时自动关闭。你不需要手动管理数据库连接——框架帮你做了。

第四讲：app/models/task.py + app/schemas/task.py — 模型与数据契约

这两个文件构成了这个项目的数据层。理解它们的区别，是理解分层架构的关键。

ORM 模型 vs Pydantic Schema

对比维度ORM 模型 (models/task.py)Pydantic Schema (schemas/task.py)
使命描述数据库表结构描述 API 契约
创建对象Task(title="...")TaskCreate(title="...")
数据库相关是（映射到 tasks 表）否（纯粹的数据结构）
验证无（靠数据库约束）有（Pydantic 自动校验）
序列化不能直接返回给 API自动转 JSON（from_attributes=True）
核心设计决策：ORM 和 Schema 分离
为什么不直接返回 ORM 对象？因为你的数据库表结构不应该决定你的 API 响应格式。今天加个字段不代表它应该暴露给调用方；今天改个列名不代表调用方要跟着改。Schema 是一层保护层。

TaskStatus 枚举

class TaskStatus(str, enum.Enum):
    pending = "pending"
    in_progress = "in_progress"
    done = "done"

继承 str 的好处：可以直接 JSON 序列化（"pending" 而不是 TaskStatus.pending）。

UUID 主键

id: Mapped[uuid.UUID] = mapped_column(
    UUID(as_uuid=True), primary_key=True, default=uuid.uuid4
)

为什么用 UUID 而不是自增整数？分布式系统里，多个服务各自生成 ID 不会冲突。自增 ID 在分库分表时会出问题。

Pydantic V2 关键特性：from_attributes

class TaskResponse(BaseModel):
    model_config = ConfigDict(from_attributes=True)
    id: uuid.UUID
    title: str

from_attributes=True 告诉 Pydantic 从 ORM 对象的 .属性 读取数据。这替代了旧的 class Config: orm_mode = True。

TaskCreate vs TaskUpdate

TaskCreate：title 必填（Field(...)）。创建时必须给标题。

TaskUpdate：所有字段可选。PATCH 语义：只传你要改的字段。你可以在请求体里只传 {"status": "done"} 而不传 title。

第五讲：app/routers/tasks.py — RESTful CRUD

这是用户能看到的 API。5 个端点，标准的 REST 风格。

端点—HTTP 动词—幂等性

端点HTTP 动词幂等？状态码查询方式
/tasksGET是（不改数据）200select(Task).order_by(...)
/tasksPOST否（每次新建）201db.add() → commit() → refresh()
/tasks/{id}GET是200/404db.get(Task, id)
/tasks/{id}PATCH部分幂等200/404model_dump + setattr
/tasks/{id}DELETE是204/404db.delete() → commit()

创建流程详解

1
请求体 {"title":"hello"} → Pydantic 校验 → 生成 TaskCreate(title="hello")
2
task = Task(title=body.title) → 创建 ORM 实例（id 自动生成 UUID，status 默认 pending）
3
db.add(task) → 把对象加入 SQLAlchemy 的 "待插入" 队列
4
await db.commit() → 发送实际的 INSERT SQL 到 PG
5
await db.refresh(task) → 从数据库重新加载（获得 PG 填充的 created_at/updated_at 时间戳）
6
return task → Pydantic 自动把 ORM 对象转成 TaskResponse JSON

PATCH 的精妙之处

update_data = body.model_dump(exclude_unset=True)
for key, value in update_data.items():
    setattr(task, key, value)

exclude_unset=True 是关键。用户在请求体里只传了 {"status": "done"}，那 update_data 就只包含 {"status": "done"}。title 不会被覆盖为 None。

为什么用 async/await？

传统的同步 Python 代码，一个请求要等数据库返回结果才能处理下一个请求。async/await 允许在等数据库的间隙去处理其他请求——一个线程可以并发处理上千个请求。

第六讲：app/routers/health.py — K8s 的生命线

这个端点只有 50 行代码，但它是 Kubernetes 判断 Pod 是否"活着"的依据。

两种探针

探针失败后果典型检查内容
livenessProbekubelet 杀掉并重启 Pod应用是否死锁/无响应
readinessProbe从 Service 端点列表中移除数据库是否可达
设计原则
健康检查不应做重操作。SELECT 1 足够——不需要建表、不需要做复杂查询、不需要创建新连接。如果 PG 不可达，直接返回 503 告诉 K8s 这个 Pod 暂时不能接流量。
